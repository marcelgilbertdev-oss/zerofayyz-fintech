# Credential Recovery

**Written 21 August 2026, after a Notes/iCloud failure destroyed several days of
saved credentials.**

Read this first, before assuming anything is lost:

> **Nothing you lost was the original.** Every secret this platform uses is
> stored *inside the service that issued it* and is already installed in the
> deployment that uses it. Losing your copy does not break anything and does not
> lock you out. The platform kept running through the whole incident.

This document never contains a secret value. It says, for each one: where it
lives, how to get a fresh copy, and what happens if you replace it. That is the
point — a recovery map is safe to keep in the repo; a list of passwords is not.

---

## The one-line summary

| Secret | Still working? | Can you see it again? | Can you replace it? |
| --- | --- | --- | --- |
| Neon connection string | Yes | **Yes** — shown on demand | Yes |
| Stripe test API key | Yes | Reveal or roll | Yes |
| Stripe webhook secret | Yes | **Yes** — shown on demand | Yes |
| Render environment variables | Yes | **Yes** — shown on demand | Yes |
| `SESSION_SECRET` | Yes | Yes, but never needed | Yes, with one side effect |
| Platform admin password | Unknown to anyone | **No** — it is hashed | **Yes — just re-seed** |

Only one row in that table is unrecoverable, and it is also the easiest to
replace.

## 1. Neon — the database connection string

**Where:** [console.neon.tech](https://console.neon.tech) → project
**zerofayyz-fintech** → green **Connect** button → branch `production`,
database `neondb`.

Shown in full, on demand, as many times as you like. It is not a one-time
reveal.

**Used by:** Render (as `DATABASE_URL`), and by you when running migrations or
the staff seed from your laptop.

**If you rotate it:** update `DATABASE_URL` in Render immediately, or the API
loses its database on next restart.

---

## 2. Stripe — API key and webhook secret

**Where:** [dashboard.stripe.com](https://dashboard.stripe.com), **Test mode on**.

- **API key** — Developers → API keys. This project uses a *restricted* key
  (`rk_test_…`) with **Checkout Sessions: Write** and nothing else. If you
  cannot reveal it, roll it and paste the new one into Render as
  `STRIPE_API_KEY`.
- **Webhook secret** — Developers → Webhooks → the `zerofayyz-fintech-api`
  endpoint → **Signing secret** (`whsec_…`), revealable on demand. Lives in
  Render as `STRIPE_WEBHOOK_SECRET`.

**Everything here is sandbox.** No real money, no customer data, nothing that
costs anything if it leaks. Rotate freely — worst case is a few minutes of
failed webhooks until Render restarts.

**If you rotate the webhook secret:** signature verification fails until Render
has the new value, and Stripe will retry the deliveries afterwards. The ledger
survives, because duplicate events are refused by a database constraint.

---

## 3. Render — where the API's environment actually lives

**Where:** [dashboard.render.com](https://dashboard.render.com) → service
**zerofayyz-fintech-api** → **Environment**.

This is the real answer to "where are my keys?" — they are here, installed and
working, and Render will show you the values. Your Notes copy was only ever a
convenience.

Variables in use: `DATABASE_URL`, `STRIPE_API_KEY`, `STRIPE_WEBHOOK_SECRET`,
`APP_URL`, `SESSION_SECRET`, `NODE_VERSION`, `NODE_ENV`, `HOST`.

`SESSION_SECRET` is generated by Render itself (`generateValue: true`) — you
never chose it and never need to know it.

**If you rotate `SESSION_SECRET`:** nothing breaks and nobody is signed out.
Session cookies do not depend on it. It only keys the privacy hash used to tell
two sessions apart, so historical fingerprints stop matching new ones — a
cosmetic discontinuity in the audit log, nothing more.

## 4. The platform admin password — the only truly unrecoverable one

`admin@zerofayyz.test` is stored as a **scrypt hash**. It cannot be read back,
by you or by anyone with the database. That is the correct design and the reason
losing it costs you nothing: you do not recover it, you replace it.

```bash
cd "/Users/marcel/Documents/ZEROFAYYZ FINTECH CLOUD PLATFORM/apps/api" && read -r "DATABASE_URL?Neon connection string: " && read -rs "ADMIN_PASSWORD?Admin password (hidden): " && echo && DATABASE_URL="$DATABASE_URL" ADMIN_PASSWORD="$ADMIN_PASSWORD" npm run seed:staff
```

**Expect:** `seeded and VERIFIED …` — the seed now reads both rows back and runs
the real verifier against them before claiming success. If it prints VERIFIED,
those credentials will sign in. If the password did not take, it raises an error
instead of congratulating you.

Safe to run as often as you like: it updates the existing rows rather than
creating duplicates, and an integration test pins that.

**The demo operator password is not a secret at all** — `view-the-ledger` is
printed on the login page on purpose. It is in the repo, in this file, and in
the seed script. Nothing is lost by publishing it, because an operator can read
everything and change nothing.

## 5. GitHub, Vercel

GitHub sign-in lives in your browser's password manager. Vercel authenticates
*through* GitHub, so recovering GitHub recovers Vercel. Neither stores anything
this project needs you to remember.

---

## 6. What to do differently

The failure was not iCloud. The failure was that **one app was the only copy**.

- **Use a password manager**, not Notes. Anything with an export you control.
- **Never treat a note as the system of record for a secret.** The system of
  record is the service that issued it — this document names all of them.
- **Keep this file current.** When a new service joins the platform, add a row
  saying where its secret lives. Never add the value.
- **Prefer secrets you can replace over secrets you must protect.** Every secret
  above is rotatable in minutes, which is why a lost notes app is an
  inconvenience rather than an incident.

## The reassuring part, stated plainly

At the moment the notes were lost, the platform was serving live traffic with
every one of these credentials installed and working — 20/20 production checks
green, database responding in 2ms, all three clients live. You never lost
access to anything. You lost a convenience copy of things the services will
hand back to you on request.
